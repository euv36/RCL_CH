## 2. Глобальные требования (не обсуждаются)

1. **Целевая платформа — Raspberry Pi 4B.** Всё, что на Pi выполняется в реальном времени (захват → декод → HSV → трекинг → serial), в конечном итоге должно работать в **C++**. Python на Pi — временный fallback, не конечное решение.
2. **Скорость.** Ориентир — не уронить текущие цифры Python-пайплайна (3 ворота, 640×360: ~25.9 fps — это потолок камеры ~26 fps; decode ≈23.5 мс, hsv ≈1.1 мс, gates ≈11.3 мс). C++-код обязан быть не медленнее и не прожорливее. **`cv2.setNumThreads(N>1)`/`cv::setNumThreads(N>1)` запрещён** — на этом Pi 4 потока декодера в 3 раза медленнее одного.
3. **Без багов.** Ошибка = робот сходит с ума на матче. Краевые случаи обрабатывай явно: hue wrap 0/179, переход угла 359→1° (это 2°, а не 358), потеря/обрыв кадра, отвал ZMQ, ошибка serial, битый JSON, нехватка памяти. Никаких «авось», никаких необработанных исключений в долгоживущих циклах, никакого роста аллокаций от кадра к кадру.
4. **Сейчас разработка и проверка — на ПК (Windows).** Всё новое должно запускаться и проверяться на Windows (system Python; корневой `.venv` — WSL-only, не использовать) **и** иметь готовый путь деплоя на Pi (`pscp`/`plink` с паролем — пароль спрашивай у пользователя; точные команды в `UniKostyl/AGENTS.md`, юзер `twox`).
5. **Оптимизация.** Не аллоцируй кадры/массивы в горячем цикле без нужды, никакого per-pixel Python, маска + `moments` (никаких `findNonZero`/`boundingRect` — их уже выкинули как hot spot, не возвращай).
6. **Идеи приходят порциями.** Пиши код модульно: новая логика — в новых файлах с чистым API, чтобы следующие идеи ложились поверх без переделки твоего кода.
7. **На Pi будут ещё тактики и датчики по I2C.** Позже на том же Pi появятся модуль тактик и обработка некоторых датчиков по I2C — пайплайн камеры не должен съедать все ресурсы: держать CPU-бюджет (ориентир — как текущий Python: ~1 ядро из 4), никаких busy-wait/spin-циклов, экономно по памяти; архитектура должна позволять добавить I2C-обработку и тактики отдельными модулями, не влезая в горячий цикл камеры.

## 3. Параллельная работа агентов (чтобы не конфликтовать)

- В корне репо есть `COORDINATION.md` (создай, если нет). Формат — таблица: агент/задача, статус (`in_progress`/`done`), файлы **WRITE** (редактируешь), файлы READ. Перед началом работы прочитай его и впиши себя; по завершении поставь `done`.
- **Железо — тоже ресурс:** камера на ноутбуке и сам Pi могут использоваться только одним агентом одновременно. Захват железа помечай в `COORDINATION.md` отдельной строкой (resource lock: `camera` / `pi`) и освобождай по завершении; если лок занят — жди/планируй PC-only проверки, не долби устройство.
- Свою логику — **в новые файлы**. Общие файлы (`cv_kostyl.py`, `unikostyl.py`, `rpi_elp_cam.py`) — только маленькие точечные вставки в явных местах (кнопка, один вызов нового модуля). Не реформатить, не переименовывать, не трогать чужие строки.
- Файл занят другим активным агентом (по `COORDINATION.md`) — **не трогай его**: запиши в `COORDINATION.md` строку `needs integration: <что и куда>`, а интеграцию сведи к однострочному вызову своего модуля; если одной строкой не выходит — остановись и спроси пользователя.
- Запрещено всем: `git commit`/`push`/`checkout`/`reset`; удаление чужого кода; изменение протоколов из раздела 4; правка legacy-файлов (`rpi_ks.py`, `OpenKostyl.py`, `mirror_unwrap.py`, `thresholds.txt`) без явного задания.

## 4. Контракты, которые нельзя ломать

- **ZMQ видео:** Pi PUB `tcp://*:5555` (JPEG); ноутбук SUB. *Разрешённое расширение — см. Идею 2 (multipart), обратная совместимость обязательна.*
- **ZMQ цвета:** ноутбук PUB `tcp://*:5557`, JSON `{"gates":[{"id":N,"rgb":[r,g,b]},...]}` + legacy `{"rgb":[r,g,b]}` (gate 1); Pi также принимает `{"stream":true|false}`. Pi делает SUB **connect**, поэтому PUB обязан биндиться на ноуте. Тест без остановки UI: порт 5567 (`out/send_colors.py <sec> 5567`).
- **Serial Pi→Arduino** `/dev/serial0` @115200: `G<id>,<angle>,<area>\n` при изменении угла на ≥3°, `G<id>,-1,0` один раз при потере ворот, `HB\n` каждые 0.5 с. Arduino парсит только G1/G2 (G3 игнорирует) — формат существующих строк менять нельзя. **Обратного канала Arduino→Pi сейчас нет**; любые телеметрия/расширения (heading, одометрия, фототранзисторная плата, EDGE) — только явное additive-расширение, предложенное пользователю на согласование, с обратной совместимостью (старая прошивка игнорирует новые строки).
- **Цвет:** ноутбук шлёт RGB (середина LAB-диапазона); Pi конвертит RGB→HSV, `inRange` с tolerance (40,100,100) (H,S,V), hue wraparound обязан работать. Порядок каналов: Pi получает **RGB**, OpenCV-конверсии ждут **BGR** — не перепутай.
- **Угол:** `atan2(center_y - cy, cx - center_x)` в градусах `% 360`; 0° = вправо, CCW.
- **Ворота на Pi стартуют выключенными** (`enabled: False`) и не трекают ничего, пока не придут цвета (или пока не загрузится файл сохранённых цветов — Идея 3). Слот с дефолтными полными порогами = «не настроен» (`slot_configured()`): не трекать, не рисовать.
- **UI-контракты:** `unikostyl.py` при import создаёт pygame-окно (не импортировать в headless); `main_loop_frame(frame_rgb)` → `(angle, {gate_id: rgb})`, вызов раз в кадр; слоты порогов 1..3 = ворота 1..3; **на самом кадре ничего не рисуется** (ни текста, ни bbox) — статус только в виджетах/консоли.
- **Порты:** 5555 видео, 5557 цвета, 5567 тест, **5559 — управление камерой (настройки), зарезервирован**.
- **Файлы-договоры:** `saved_gates.json` (сохранённые цвета ворот, Идея 3), `camera_settings.json` (настройки камеры, Идея 1), `distance_calib.json` (калибровка дистанции, Идея 6), `field_map.json` (привязка к полю и карта, Идеи 10–11) — схемы в разделе 5. Запись **атомарная** (tmp + rename): Pi может потерять питание посреди матча.
- **Запреты:** не возвращать автоэкспозицию (стабильные цвета между кадрами важнее); `rpi_elp_cam.py` не удалять, пока C++-ядро не принято на Pi; низкие режимы камеры (720p и ниже) не использовать как «уменьшение» — это сенсорные кропы, полный FOV только 1920×1080 с программным даунскейлом.

**Факты регламента — RoboCupJunior Soccer, IR-лиги («Автономный робофутбол RoboCup infrared»)** — официальные правила: `https://robocup-junior.github.io/soccer-rules-entry/master/rules.html` (у российских турниров бывают локальные вариации — сверяй с регламентом конкретного соревнования и делай размеры конфигурируемыми):
- Поле 110–160 см × 180–225 см; стены 10–25 см (матово-чёрные); пол — зелёный ковёр; белые линии разметки 20 мм ±10%. В стенном варианте (Entry) выезда за поле нет вообще; в локальных безстенных вариантах (например, поле 1220×1830 мм с белой граничной полосой 300 мм) выезд за границу — нарушение. **Подтверждено пользователем 2026-11-17: площадка СО СТЕНАМИ (Entry-вариант)** — выезда за поле нет физически; детектор границы (Идея 11) — вспомогательный, приоритет ниже; размеры оставить конфигурируемыми на случай смены площадки.
- Ворота: внутренняя ширина 45–60 см, глубина 74 мм, высота = стенам; один — **жёлтый**, второй — **синий** (это и есть цвета трекинга ворот).
- Выезд за поле/выбивание мяча из поля → робот «damaged»: убирается минимум на 1 минуту (локальные регламенты — до нескольких минут). Граница поля — критическая функция (Идея 11).
- Мяч — пульсирующий ИК: 920–960 нм, несущая 40 кГц, модуляция 1.2 кГц, ⌀74 мм (Entry); в 2:2-лигах переходит на оранжевый ИК-мяч ⌀42 мм. **Камера мяч не трекает без явного задания** — мяч ищут ИК-приёмники.
- Матч: 2 тайма по 10 минут; гол = мяч коснулся задней стены ворот.

## 5. Задачи (идеи)

### Идея 1 — Окно настроек камеры (экспозиция и др.)
Отдельное окно, открывается **только по кнопке** в главном UI (основной интерфейс не захламлять; допустимая альтернатива — сворачиваемая панель внутри главного окна, но по умолчанию — отдельное окно). Контролы: exposure (ручной), gain, brightness, gamma, saturation, contrast, power_line_frequency (50 Гц), exposure_dynamic_framerate (выкл). Диапазоны V4L2 — в `UniKostyl/AGENTS.md` (exposure 1..5000, gain 0..100, brightness −64..64, gamma 72..500, saturation 0..128, contrast 0..64). Два бэкенда:
- **Локальная камера на ПК** (`fisheye.open_camera`, MSMF+MJPG): применять через `cv2.CAP_PROP_*` и **читать обратно** — MSMF врёт о применённом значении; неподдерживаемый контрол показывать «н/д», не молчать.
- **Камера Pi:** ноутбук PUB `tcp://<pi>:5559` → на Pi мини-сервис **`rpi_cam_ctl.py`** (новый файл, SUB connect на ноут — как у цветового SUB) применяет контролы через `v4l2-ctl` батчем с повтором по одному при отказе (тот же паттерн, что `v4l2_set` в `rpi_elp_cam.py`). На Pi никакого GUI.
Правила: автоэкспозицию не включать; яркость (brightness) без нужды не поднимать — вымывает цвета (HSV S 168→20); кнопка «безопасные дефолты» (gain=0, brightness=0, exposure≈300 — см. verified-настройки в `UniKostyl/AGENTS.md`); всё сохранять в `camera_settings.json` (атомарно, обе стороны) и авто-применять при старте Pi **после** CLI-флагов. Реализация окна — cv2-трекбары (прокачивай `cv2.waitKey(1)` в главном цикле, пока окно открыто) или pygame-панель — на твой выбор. Трекбары fisheye — отдельная сущность, не смешивать. Интеграция в `cv_kostyl.py` — одна кнопка + один вызов.

### Идея 2 — Понятный и красивый UI
Панель статуса ворот 1..3: настроен/не настроен (свотч цвета), **найден/потерян (live)**, угол/площадь, FPS обработки; индикация источника видео (локальная камера / Pi-стрим + адрес) и статуса публикации цветов (5557). Стиль — аккуратные панели, цветовые коды ворот yellow/blue/orange (как `TRACK_COLORS`); использовать примитивы `widgets.py`. Ничего не рисовать на самом кадре (конвенция проекта). Не ронять FPS отрисовки; контракт `main_loop_frame` сохранить. Статус «найден/потерян/угол» должен приходить от **реального** трекинга, а не заглушки: для Pi-стрима расширь публикацию 5555 до multipart ZMQ `[JPEG, JSON-статус]` (JSON: `{"gates":{"1":{"found":true,"angle":123.4,"area":456,"dist_cm":148.0,"dist_reliable":true},"2":...},"fps":25.9}` — поля `dist_*` добавляются Идеей 6, до её внедрения они опускаются), ноутбук обязан принимать **и старый** одиночный JPEG, **и новый** multipart — обратная совместимость. С Pi-стороны для статуса достаточно маленькой добавки в `rpi_elp_cam.py`; C++-ядро (Идея 4) повторит то же самое.

### Идея 3 — Сохранение 3 цветов ворот (персистентность)
Файл **`saved_gates.json`** — рядом с `cv_kostyl.py` (ноут) и `/home/twox/` (Pi). Схема:
```json
{"version": 1, "gates": {"1": {"rgb": [r,g,b], "lab": [Lmin,Lmax,Amin,Amax,Bmin,Bmax] | null, "enabled": true, "ts": "..."}, "2": {...}, "3": {...}}}
```
Логика: слоты G1..G3 (одновременно максимум 3). Захват `SAVE Gn` → **немедленная атомарная перезапись** слота n — новый цвет слота заменяет прежний. Старт ноутбука: загрузить файл → восстановить слоты (LAB-пороги, если сохранены) → автосохранить цвета в Pi. Старт Pi: загрузить файл → ворота активны сразу, **ноутбук не нужен** — главное требование: после перезапуска Pi цвет не выделяем заново. Pi обновляет свою копию файла при получении цветов по 5557. Сейчас реализовать добавкой в `rpi_elp_cam.py` (маленькой), затем повторить в C++-ядре. С legacy `thresholds.txt` не смешивать (его не трогать).

### Идея 4 — C++-ядро на Pi
Новый каталог **`UniKostyl/pi_core/`** (Python-файлы не трогать, кроме момента переключения). Полная замена `rpi_elp_cam.py`: V4L2 MJPG 1920×1080 (полный FOV), декод `IMREAD_REDUCED_COLOR_2` (640×360), HSV `inRange` + `moments` на 3 цвета, кластеризация кусков и гистерезис потери (Идея 5), дистанция по калибровке (Идея 6), self-маска корпуса (Идея 8), JPEG PUB 5555 (+ multipart статус Идеи 2), SUB 5557 цвета, SUB 5559 настройки камеры (v4l2-ioctl), serial по контракту раздела 4, `saved_gates.json` + `camera_settings.json` + `distance_calib.json` (атомарно), старт с выключенными воротами до прихода цветов/загрузки файла. Зависимости: libzmq (+cppzmq header-only) и nlohmann/json single-header — vendoring заголовков в `pi_core/vendor/`, `libzmq3-dev` на Pi ставить через apt только с пароля пользователя. Сборка: CMake Release, `-O3`, `cv::setNumThreads(1)`. Структура: чистая логика (tracker, gate_store, применение настроек) отделена от IO (capture/net/serial), чтобы логику можно было собрать и проверить где угодно. Заложи запас под будущие модули Pi (тактики, обработка I2C-датчиков): пайплайн камеры занимает ~1 ядро (как текущий Python), без busy-wait; будущие компоненты добавляются отдельными модулями/потоками, не влезая в горячий цикл. CLI-флаги зеркалируют `rpi_elp_cam.py` (`--laptop-ip`, `--gates`, `--track-size`, `--stream-size`, `--stream-fps`, `--no-stream`, `--no-serial`, `--duration`, `--probe`) + `--print-serial` (serial-строки в stdout вместо устройства — smoke без Arduino). Живучесть: на матче ничего не падает — обрыв ZMQ/serial/камеры = лог + retry/деградация (ворота off по таймауту без цветов), память не растёт от кадра к кадру. Stage-тайминги логировать в том же формате, что Python (decode/hsv/gates мс). Переключение на ядро — только после прохождения smoke-тестов раздела 6 на Pi; `rpi_elp_cam.py` остаётся rollback-путём.

### Идея 5 — Ворота не «разбросаны»: кластеризация кусочков и стабильность
Проблема: после захвата цвета (например, случайно совпавшего с цветом майки/предмета) маска находится мелкими кусками в разных местах кадра. Ворота на соревнованиях всегда в одном месте, НО робот-противник стоит перед воротами и может разрезать их на куски — поэтому близкие куски надо сливать, а далёкую мелочь отбрасывать. Референс-пайплайн (по фото): mask → erode + dilate (снять шум) → самый крупный объект через `minEnclosingCircle` → angle через `atan2` → radius → distance. Требования:
- **Морфологическая чистка:** после `inRange` — morphologyEx OPEN (erode+dilate), размер ядра — настраиваемый параметр.
- **Слияние близких кусков в одни ворота:** компоненты с зазором < `merge_gap_px` (настраиваемый, дефолт ~2-3% ширины кадра, подбрать на живой картинке) — ОДНИ ворота (зазор = корпус противника). Реализация: dilate маски радиусом слияния перед `connectedComponentsWithStats`, либо кластеризация компонентов по зазору. Результат — один объект: `moments` (центр/угол) + `minEnclosingCircle` (радиус/размер).
- **Отброс «разбросанных» кусков:** `min_gate_area` (настраиваемый, масштабируется с разрешением) — мелочь не ворота; компонент, отстоящий от центроида основных кусков дальше `max_stray_px`, — посторонний предмет (майка), отбрасывать. Максимум один объект ворот на цвет.
- **Гистерезис, чтобы робот не «сходил с ума»:** ворота считаются потерянными только после N подряд пустых кадров (дефолт 5, настраиваемый) — и только тогда шлётся `G<id>,-1,0` (формат контракта не меняется, меняется момент срабатывания); новый детект принимается после M подряд кадров; при двух конкурирующих кластерах (майка + ворота) держаться кластера ближе к предыдущей позиции ворот, пока новый не стабилен M кадров.
- Всё реализовать в Python (`rpi_elp_cam.py` + ноутбучный трекинг) **и затем в C++-ядре Идеи 4 — паритет логики**. Производительность: `connectedComponentsWithStats` + morphology на 640×360 дёшевы; никаких findNonZero/boundingRect; stage-тайминги в лог. Legacy `mirror_unwrap.py` — только справочник, не оживлять.

### Идея 6 — Расстояние до ворот по их размеру (калибровка)
- Размер ворот брать от слитого кластера Идеи 5: ширина или радиус `minEnclosingCircle` в px (шаг 5 референса).
- Модель — эмпирическая кривая как на референсе: `d = a / (b - r) - c`, где r — радиус/полуширина объекта в px, d — расстояние в см; константы a,b,c подгоняются по калибровочным точкам (робот на известных дистанциях → снять r). Константы хранить в **`distance_calib.json`** (атомарная запись, схема: `{"version":1,"model":"a/(b-r)-c","a":...,"b":...,"c":...,"points":[[r_cm,r_px],...],"ts":...}`). Сверка/фолбэк без калибровки — существующая модель `Z = KNOWN_TARGET_WIDTH_CM * (w/π) / w_px` в `unikostyl.py`.
- **Калибровщик:** режим/скрипт, собирающий пары (известная дистанция → измеренный r) и фитящий a,b,c (4-6 точек), с записью JSON. Должен работать с живой камерой и с сохранёнными кадрами.
- **Защита от мусора (без багов):** клэмп `r < b - ε` (деление!), клэмп d в рабочий диапазон (0..500 см); при частичном перекрытии ворот противником видимый размер занижен → помечать дистанцию как ненадёжную (поле `dist_reliable: false` в статус-JSON Идеи 2) и держать последнее надёжное значение T секунд.
- Дистанция выводится в статус-JSON (Идея 2), радар (Идея 7) и посекундный лог. Реализация — Python + C++-ядро (паритет).
- Реальную ширину ворот для аналитической модели — из регламента: внутренняя ширина ворот 45–60 см (факты в разделе 4); конкретное значение турнира сделать параметром.

### Идея 7 — Радар-окно («кружочек»)
Кнопка в окне настроек (Идея 1) открывает радар как на референсе: чёрный диск с тонкой окантовкой, в центре светлый круг — зона корпуса робота (совпадает с self-маской Идеи 8); настроенные ворота рисуются дугами своего цвета (yellow/blue/orange) на своих углах вокруг центра; текущая цель (TARGET G1..G3 / мяч) — маркер-кружок с линией от центра и подписями «угол°» (как «52°» на референсе) и «r = N px → M см» (дистанция из Идеи 6). Обновляется в реальном времени, показывает все активные ворота одновременно. Источник данных: локальный режим — что насчитал ноутбучный трекинг; Pi-стрим — статус-JSON Идеи 2. Углы — строго из того же источника, что и трекинг (в RING-режиме угол из x-позиции полосы, не atan2 — не рассинхронить радар с реальным поведением). Реализация: cv2-окно или панель в главном UI — на выбор агента (второе окно pygame без pygame-ce не делать). Новых ZMQ-портов не добавлять.

### Идея 8 — Вырезание корпуса робота из области поиска цвета
Робот не должен находить цвет сам на себе: зона корпуса программно исключается из поиска ДО `inRange`/`moments` — ни один кусок на корпусе не сможет образовать «ворота».
- Реализация: маска-исключение (внутренний круг вокруг центра зеркала/линзы; опционально кольцо с внешним радиусом — референс использует mask `r 110..355 px`) применяется на обеих сторонах: ноутбук (unikostyl/fisheye-пайплайн) и Pi (`rpi_elp_cam.py` сейчас, `pi_core` потом).
- Параметры (cx, cy, внутренний/внешний радиус в px или % от min(w,h)) — отдельная секция `self_mask` в `camera_settings.json`, редактируется в окне настроек Идеи 1 (трекбары с живым превью зоны на кадре).
- Дефолт согласовать с текущими `cut center %` (RING) и `ZONE_RADIUS_FRAC = 0.25`. Это отдельная сущность: ZONE_RADIUS_FRAC — зона вывода угла на экране, self_mask — запрет поиска цвета. В коде не смешивать.

### Идея 9 — Роли ворот: «наши» / «противника»
- В окне настроек (Идея 1, секция ворот) для каждого настроенного слота выбирается роль: `наши` / `противника` / `не задана`. По регламенту ворота жёлтый и синий — соответствие «цвет ↔ роль» задаёт пользователь.
- Роль сохраняется в `saved_gates.json` (поле `role` в слоте) — переживает рестарты вместе с цветом (Идея 3).
- UI: в панели статуса (Идея 2) и на радаре (Идея 7) — бейджи «НАШИ» (зелёный) / «ПРОТИВНИК» (красный); на радаре стрелкой можно показывать направление атаки — к воротам противника.
- Статус-JSON (Идея 2): поле `role` у каждого ворота.
- Если роль понадобится Arduino (поведение движения) — только additive-расширение serial по правилу обратного канала из раздела 4, двусторонне, с игнорированием новых строк старой прошивкой. Без явного задания это не делать.

### Идея 10 — Привязка к полю: запоминание положения робота
Проблема: квадратная матрица камеры — при повороте робота ворота выходят из FOV. Нужна «привязка к полю», выполняемая при первичной настройке — когда робота ставят для захвата цветов ворот:
- **Процедура:** кнопка «Привязать к полю» → система фиксирует «полевой кадр»: для каждого настроенного ворота угол + дистанция (данные Идей 5–6) относительно робота в момент привязки; пользователь дополнительно указывает позицию робота на поле пресетом (центр / у своих ворот / произвольная точка) и куда смотрит камера относительно поля — приближённая привязка, не SLAM.
- Хранить в **`field_map.json`** (атомарно): полярные координаты ворот относительно робота, пресет позиции, ориентация, время. Схема `{"version":1,"bound_at":"...","robot_pos":"center|own_goal|manual","gates":{"1":{"angle_deg":...,"dist_cm":...,"estimated":false},...},"heading_offset_deg":...}`.
- **Дослепывание при потере FOV:** пока ворота вне вида, радар (Идея 7) и статус показывают «последние известные» направления с пометкой `estimated: true` (приглушённо/пунктиром). Учёт накопленного поворота робота — ТОЛЬКО если появится обратный канал Arduino→Pi (heading/одометрия): сейчас его нет, поэтому агент обязан сначала обследовать `uart_rpi.ino`, **предложить** минимальное additive-расширение (например, строка `O<heading_deg>\n` или тики энкодеров + состояние фототранзисторной платы) и согласовать с пользователем до реализации. Старая прошивка должна продолжать работать.
- Без обратного канала — честная деградация: статический полевой кадр + пометки «est» без учёта поворота; канал молча не придумывать.

### Идея 11 — Граница поля: фототранзисторная плата + камера (fusion)
Мотивация: выезд за поле = робот «damaged», убирают минимум на минуту (факты регламента в разделе 4). Сейчас границу видит только Arduino с платой отражения: **фототранзистор + светодиод, фототранзистор включён по схеме усилителя с общим коллектором**. Требование: робот определяет границу поля **и по плате линий, и по камере**, совместно.
- **Камерный детектор границы:** пол — зелёный ковёр, разметка — белые линии 20 мм, вне поля — стол/чёрная поверхность/граничная полоса. По видео вниз (RING/направленный вид) оценивать наличие и дальность края поля по секторам вокруг робота (8–12 секторов): отдельный HSV-диапазон пола (+белая линия), доля «не-пола» в секторе → «край близко». Дёшево: downscale + HSV + пороги по секторам, никакой тяжёлой сегментации. Реализация в Python и C++-ядре — паритет.
- **Fusion:** опасность в секторе = (камера видит край) OR (плата линий сработала). Состояния платы у Pi сейчас нет — тот же additive-обратный канал, что в Идее 10 (например, состояния сенсоров в строке телеметрии). Если канал не реализован, камерный детектор работает самостоятельным «советчиком» и ничего не блокирует.
- **Вывод:** статус-JSON (Идея 2) — флаги/сектора «край близко»; радар (Идея 7) — подсветка опасных секторов и рамка/контур поля по `field_map.json`; Arduino — только через согласованное additive-сообщение (например, `EDGE\n`), поведение Arduino по умолчанию не менять.
- **Без ложных срабатываний:** пороги настраиваемые (в `field_map.json`, калибровка на реальном поле), гистерезис — опасность подтверждается 2–3 кадрами подряд; показания платы имеют приоритет над камерой. Тестировать на записанных кадрах реального поля, не только на синтетике.

### Идея 12 — Перенос игровой логики RCJ_NEW с Arduino Mega на Pi (Arduino = моторы + гироскоп + кикер)
**Приоритет — камера: эта задача выполняется ТОЛЬКО по отдельному промпту `PROMPT_ROBOT.md` (отдельный агент, не трогающий камерные файлы); в рамках основного промпта Идею 12 не брать.**
Эталонные исходники: **`UniKostyl/rcj_arduino_src/`** — копия прошивки Arduino Mega 2560 (sketch + AGENTS.md с верифицированными деталями — прочитай его). Требуемый итог: **Arduino — тонкая прошивка** (моторы, гироскоп MPU6050, кикер, дрибблер-серво, сырой опрос линий, ловушка-микрик); **Pi (`pi_core`) — вся игровая логика на C++** (тактики, мяч, линии-вычисления, ворота, fusion).
- Факты эталона: тактики в `controller.cpp` (`play()`, роли `GOALKEEPER`/`FORWARD` через `config.hpp`, `alignBallGate`, `catchBall`, `score`, `findGate`, `driveFromLine`, `followBallWithRotation`, `turnToBall`); мяч = **Locator по I2C 0x0E** (регистры: 0x04 angle, 0x05 strength, 0x06 angleClose, 0x07 strengthClose; `distance = 10000/strength`), ловушка = микрик pin 14; линии = 16 датчиков через 4-канальный мультиплексор на A14 (ADC Mega, веса/углы в `line.cpp`); ворота сейчас приходят с Pi в legacy-формате `angle,area` на Serial2 115200 (в pi_core они есть напрямую — по serial не нужны); кикер pin 18, дрибблер Servo pin 12, MotorPWM=70, BS=100/LS=60.
- **Разделение (решение пользователя, не менять):** Arduino — исполнитель: приём **4 PWM колёс + бит кикера + бит дрибблера**, применение `MotorInvert[]`/лимитов/`MotorMinPWM[]` (safety-путь motors.cpp), MPU6050 DMP с фризом дрейфа (`gyro.cpp` целиком остаётся там, тайминг 100 Гц) + телеметрия heading ≥100 Гц (со флагом still), сырой опрос 16 линий (mux+ADC) в телеметрию, микрик pin 14. Pi (`robot_core`) — вся стратегия: локатор (`ball.cpp`: **I2C Locator 0x0E подключается к шине Pi** — проверить уровни 3.3В/5В, при 5В обязателен level shifter), тактики (`controller.cpp`), omni-микс «угол→4 PWM» + PI/PD удержания курса (gains из `controller.hpp`) на телеметрии гиро, вычисление угла линий (`line.cpp`), fusion с камерой (Идея 11), ворота.
- **Новый двунаправленный serial-протокол — сначала проект, потом код, согласовать с пользователем:** Pi→Arduino: 4 знаковых PWM (−255..255) + бит кикера + бит дрибблера + STOP; Arduino→Pi телеметрия ≥100 Гц: heading (со флагом still), 16 сырых значений линий, ловушка, `HB`. **Watchdog на Arduino:** нет команд от Pi > 300 мс → моторы стоп (робот не «сойдёт с ума» при отвале Pi). Это тот самый обратный канал из Идей 10–11 — Идея 12 его реализует; новая прошивка заменяет `uart_rpi.ino` (старую не удалять). Детальный промпт этой задачи — **`PROMPT_ROBOT.md`**.
- **Портинг блокирующих вызовов:** тактики построены на блокирующих `driveForward(3000)` и т.п. — на Pi это переписывается в НЕблокирующий автомат состояний с фиксированным циклом тактик 50–100 Гц в отдельном потоке; PWM-команды стримятся непрерывно. PI/PD-законы (`driveDirection`/`drivePD`) переносятся на Pi и замыкаются на телеметрию гиро.
- **CPU-бюджет** (п.7 раздела 2): камера ~1 ядро; тактики — отдельный поток с фиксированной частотой; I2C Locator ~50 Гц достаточно; никакого busy-wait.
- Проверка: прошивка собирается через PlatformIO (рецепт в AGENTS.md эталона); логика тактик — юнит-тесты на ПК с симуляцией мяч/линии/ворот (без железа); smoke на Pi по разделу 6.
