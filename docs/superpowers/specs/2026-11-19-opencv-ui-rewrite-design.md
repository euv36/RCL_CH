# Дизайн: нативный клиент UI на OpenCV (аналог `cv_kostyl.py`)

Дата: 2026-11-19
Ветка: `native-optimization`

## 1. Зачем

Пользователь хочет прежний сценарий старого проекта: запустить один файл на ноутбуке,
ввести IP Pi в поле `Camera Source`, нажать `CONNECT` — и получить окно с живой камерой
и всеми знакомыми функциями. Задача исходного проекта — переписать старый Python-проект
на C++ и исправить баги, а не заменять его другим UX.

Сейчас этого нет: `camera_laptop_ui.exe` (SDL2 + ImGui) умеет слать команды на Pi, но
подписки на видео 5555 и декодирования JPEG нет — панель `ВИДЕО` только печатает текст.
Отдельная программа-просмотрщик была создана, признана ненужной и полностью удалена.
Пользователь явно выбрал **альтернативный путь**: переписать UI на OpenCV, «чтобы всё
было как в прошлом не переписанном проекте», перенести все старые функции и сохранить
новые.

**Разделение ролей (уточнено пользователем).** Робот работает автономно: Pi тратит ресурсы
на обработку камеры, тактику и другие нужные роботу функции, а на ПК отрисовывается
**весь** интерфейс. Pi передаёт на ПК картинку с камеры (и вспомогательный статус);
вся обработка, необходимая для отображения UI (трекинг, LAB-маски, RADAR, HSV, дистанции),
выполняется на ПК по образцу legacy `cv_kostyl.py`. После отключения Pi от ПК робот
продолжает работать автономно — ПК нужен только для наблюдения/настройки.

## 2. Цели / не-цели / анти-цели

**Цели**
- Один запускаемый файл на ноутбуке: подключение по IP к Pi, живое видео в окне.
- Перенос **всех** функций старого UI: источники видео, трекинг и LAB-пороги, цвета/роли
  ворот, сохранение, CAM SET, RADAR, HSV MASK, INFO, статус, привязка поля, диагностика.
- Сохранение новых возможностей нативной версии: serial-мост с проверкой Arduino,
  fps/статус, конфиги, атомарная запись.
- Поведенческий паритет контракта: JSON-схемы 5555/5557/5559, тайминги повторной отправки,
  правило «статус разбирается до декодирования JPEG», `unset` не передаётся по проводу,
  `EDGE` — только совет в UI/радаре.

**Не-цели**
- Переписывать `camera_service` на Pi и уже портированные алгоритмы зрения (Pi продолжает
  автономную работу; изменения нужны только на стороне ПК).
- Менять прошивку Arduino / serial-протокол / физически трогать Arduino.
- Делать слой совместимости с pygame или запускать Python.
- Port-scan, сон ноутбука, подключение к Pi без явного разрешения.

**Анти-цели**
- Очередная отдельная программа-просмотрщик вместо единого UI.
- «Красивый» интерфейс ценой потерянных функций старого проекта.

## 3. Ограничения

- C++17, MSYS2 MinGW64, OpenCV 5, libzmq (уже есть в зависимостях), существующая CMake-структура.
- Комментарии к функциям — на русском; ответы пользователю — кратко, на русском.
- Все тесты через `CAMERA_TEST_CHECK`; полный MSYS2-прогон без `-j` должен оставаться зелёным.
- Отдельный commit, русская запись в `FIX_LOG.md`, `git push origin native-optimization` без force.
- Raspberry Pi: только по явному разрешению, IP `10.132.122.51`, user `twox`, helper `raspi.ps1`.

## 4. Подходы (рассмотрены)

1. **Добавить видео в текущий ImGui UI** — самый дешёвый путь, но пользователь его
   отклонил: нужен интерфейс «как в прошлом проекте», а не ImGui-панели.
2. **Новый клиент на OpenCV HighGUI** (выбран) — максимально близко к `cv_kostyl.py`:
   `cv::imshow`, `cv::setMouseCallback`, `cv::createTrackbar`, отдельные окна CAM SET / RADAR /
   HSV MASK, те же раскладка и органы управления. Позволяет переиспользовать уже
   портированные C++-модули зрения и не ломать существующие цели/тесты.
3. Гибрид с встроенным Python/другим UI-фреймворком — отклонён: не нативный путь и
   добавляет зависимость.

Решение пользователя: подход 2.

## 5. Архитектура и переиспользование

Новая цель `camera_ui` (файл `src/laptop/opencv_main.cpp`) — точка входа по образцу
`cv_kostyl.main_loop()`: цикл захвата → подготовка RGB → кадр UI → отправка 5557 →
`pump` окон → FPS-диагностика.

**Уже портировано, переиспользуем без изменений:**
- `camera_vision` — `distance`, `hsv_color`, `gate_cluster`
- `camera_vision_cv` — `self_mask`, `tracking`, `calibration`
- `camera_common` — `gate_store`, `field_map`, `cam_settings_config`, `atomic_file`, `json_config`
- `camera_laptop_core` — `state`, `source_controller`, `clipboard_text`, `help_ru`,
  `radar_panel`, `cam_settings_panel`, `theme`
- `camera_laptop_hsv`, `camera_laptop_preview` — OpenCV-хелперы маски/превью

**Новые модули (чистые, без UI, с тестами):**
- `pi_video_client` — ZMQ `SUB tcp://<ip>:5555`, `SUBSCRIBE ""`, `CONFLATE=1`,
  `recv_multipart(NOBLOCK)`, разбор статуса до `imdecode`, `imdecode` JPEG → RGB.
  Локальный пайплайн трекинга запускается на **каждом** кадре, включая Pi-поток, как в
  legacy: кадр 640x360 поворачивается на 90° CCW → 360x640 и масштабируется до
  портретных 720x1280 перед `TrackingEngine::track`. Это даёт RADAR/HSV/LAB и локальный
  fallback StatusPanel из локально посчитанных результатов, а не только из JSON Pi.
  При отключении Pi ПК продолжает показывать последний кадр и работает автономно как
  инструмент наблюдения; робот при этом не зависит от ПК.
- `status_panel` — разбор JSON статуса (ключи `"1".."3"`), `stale = 2.0 c`, сводка
  `src/fps/gates`, устойчивость к битому JSON. JSON — **вспомогательный** источник:
  панели UI строятся из локально посчитанных результатов, как в legacy.
- `gate_publisher` — PUB 5557, `build_gate_payload()` (`gates:[{id,rgb,role?}]`, legacy
  `rgb` для G1), автоresend восстановленных цветов 10 c / 2 c и повтор на CONNECT.
- `cam_settings_client` — PUB 5559, 8 контролов, **только `cmd:set`** (Pi-слушатель
  `CamSettingsListener` не понимает `get` и не имеет канала ответа; `get` из плана
  исключён), повтор каждые 5 c, принудительный `auto_exposure=1`, предупреждение при
  `brightness > 0`.
- `ui_widgets_cv` — кнопки, слайдеры, списки, поле ввода, лог, область выделения,
  нарисованные средствами OpenCV поверх кадра (вместо pygame-виджетов).
- `field_boundary` (опционально, фаза 3) — советник EDGE-секторов из `field_map.json`,
  без serial/zmq, отключён в RING-режиме.

**Окна (как в legacy):**
- Главное `Camera`: верхний ряд `R/+/-`, `Bitmap|L|A|B`, `PAUSE`, `CAM SET`, `RADAR`,
  `BIND FIELD`, `POS`, `HSV MASK`, `INFO`; два изображения `img_src`/`img_proc`; справа
  `Camera Source` + `CONNECT` + LogPanel + StatusPanel + RadarPanel; внизу 6 слайдеров
  L/A/B, список `Gate 1..3 / Thr 4..5`, `TARGET G1..G3`, `SAVE G1..G3`.
- `CAM SET` — 8 trackbars + canvas-кнопки `SAFE DEFAULTS`, `SAVE NOW`, `SEND TO PI`,
  `backend local/pi`, `role1/2/3_ours|opponent|unset`; `SAVE_DEBOUNCE=1.0 c`.
- `RADAR` — 440x440, чёрный диск, тики 30°, дуги ворот, цель, roles/est/EDGE, ESC/крестик.
- `HSV MASK` — letterbox, легенда G1/G2/G3; ESC/крестик.
- `INFO` — модальный overlay, 7 вкладок `main/gates/radar/camera/hsv/field/status`.

Координация `waitKey`: вызывается только в одном активном окне (как legacy через
`cam_ui.is_open()`).

## 7. Поставка по фазам

1. **Фаза 1 — «видно камеру и всё под рукой» (обязательная).** Новый `camera_ui`:
   подключение по IP, SUB/JPEG/статус 5555, PUB 5557/5559, главное окно с видео,
   цвета/роли/SAVE, CAM SET, INFO, статус и лог. Это закрывает главную жалобу пользователя.
2. **Фаза 2 — полный перенос.** Локальная камера, LAB-пороги и калибровка по выделению,
   трекинг, RADAR, HSV MASK, привязка поля, `POS`, fisheye, автоматические повторы.
3. **Фаза 3 — продвинутое и диагностика.** FIELD BOUNDARY советник, посекундный лог
   cap/pre/ui/pump, паритет-тесты, финальная вычитка контракта.

Все фазы — один и тот же исполняемый файл; фазы 2/3 добавляют функции, не меняя запуск.

## 8. Тестирование

- Новые чистые helper-ы покрываются unit-тестами через `CAMERA_TEST_CHECK`
  (разбор статуса, payload ворот, конфиг клиента, stale, корректность JSON).
- Интеграционный loopback-тест: фейковый ZMQ PUB на портах 15555/15557/15559 → клиент
  получает `[JPEG, JSON]`, разбирает статус и публикует цвета; без Pi и без камеры.
- Сохранение существующих 30 тестов зелёными; полный MSYS2 `ctest` без `-j`.
- Живая проверка с Pi только после явного разрешения: smoke `pi_service_smoke.py`,
  затем запуск `camera_ui.exe` с IP `10.132.122.51`.

## 9. Решения, принятые мной (проверить при чтении)

- Старый ImGui-цель `camera_laptop_ui` **оставляем собираться** (не удаляем): он не мешает,
  а удаление ломает текущие тесты/сборку. Новый `camera_ui` — основной путь запуска.
- Окна делаем отдельными cv2-окнами, как в legacy, а не одним «комбинированным».
- `field_boundary` остаётся советником: не шлёт `EDGE` в serial.
- `EDGE`/serial и прошивку не трогаем; Arduino физически отключён.
- Трекинг локально запускается и на Pi-кадре (поворот + resize до портрета) — по образцу
  legacy, чтобы RADAR/HSV/LAB не зависели только от JSON.
- `cmd:get` на 5559 исключён: Pi-слушатель умеет только `set` и не отвечает.
- `fisheye` — только селектор режима с pass-through (в этой копии legacy он отключён).
- `thresholds.txt` — только совместимость файла, без нового I/O-модуля.
- Pi остаётся автономным роботом: он не зависит от ПК, шлёт видео и вспомогательный
  статус, а весь UI и его обработка живут на ПК (как в legacy `cv_kostyl.py`).
