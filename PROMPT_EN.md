## 2. Global requirements (non-negotiable)

1. **Target platform — Raspberry Pi 4B.** Everything running in real time on the Pi (capture → decode → HSV → tracking → serial) must ultimately run in **C++**. Python on the Pi is a temporary fallback, not the end state. Maximum possible amount of code lives in C++.
2. **Speed.** Benchmark: don't regress the current Python pipeline numbers (3 gates, 640×360: ~25.9 fps — the camera ceiling ~26 fps; decode ≈23.5 ms, hsv ≈1.1 ms, gates ≈11.3 ms). C++ code must be no slower and no hungrier. **`cv2.setNumThreads(N>1)` / `cv::setNumThreads(N>1)` is forbidden** — on this Pi a 4-thread decoder is 3× slower than 1 thread.
3. **No bugs.** A bug = the robot goes insane mid-match. Handle edge cases explicitly: hue wrap 0/179, angle crossing 359→1° (that's 2°, not 358), frame loss/dropout, ZMQ disconnect, serial errors, malformed JSON. No "hope for the best", no unhandled exceptions in long-lived loops, no per-frame allocation growth.
4. **Development and verification are on PC (Windows) right now.** Everything new must run and be verified on Windows (system Python; the root `.venv` is WSL-only, do not use it) **and** have a ready deploy path to the Pi (`pscp`/`plink` with password — ask the user for the password; exact commands in `UniKostyl/AGENTS.md`, user `twox`).
5. **Optimization.** Don't allocate frames/arrays in the hot loop without need, no per-pixel Python, mask + `moments` (no `findNonZero`/`boundingRect` — they were already removed as a hot spot, never bring them back).
6. **Ideas arrive in batches.** Write modular code: new logic in new files with clean APIs, so future ideas layer on top without reworking your code.
7. **More is coming on the Pi: tactics and I2C sensors.** Later, the same Pi will also run a tactics module and processing of some sensors over I2C. The camera pipeline must not eat all the resources: keep a CPU budget (benchmark — like the current Python: ~1 core out of 4), no busy-wait/spin loops, frugal memory; the architecture must allow adding I2C handling and tactics as separate modules without touching the camera hot loop.

## 4. Contracts that must not break

- **ZMQ video:** Pi PUB `tcp://*:5555` (JPEG); laptop SUB. *Allowed extension — see Idea 2 (multipart), backward compatibility mandatory.*
- **ZMQ colors:** laptop PUB `tcp://*:5557`, JSON `{"gates":[{"id":N,"rgb":[r,g,b]},...]}` + legacy `{"rgb":[r,g,b]}` (gate 1); the Pi also accepts `{"stream":true|false}`. The Pi does SUB **connect**, so the PUB must bind on the laptop. Test without stopping the UI: port 5567 (`out/send_colors.py <sec> 5567`).
- **Serial Pi→Arduino** `/dev/serial0` @115200: `G<id>,<angle>,<area>\n` when the angle changes by ≥3°, `G<id>,-1,0` once when a gate is lost, `HB\n` every 0.5 s. The Arduino parses only G1/G2 (G3 is ignored) — the format of existing lines must not change. **There is no Arduino→Pi reverse channel today**; any telemetry/extensions (heading, odometry, phototransistor board, EDGE) — only as an explicit additive extension proposed to the user for approval, with backward compatibility (old firmware ignores new lines).
- **Color:** the laptop sends RGB (midpoint of the LAB range); the Pi converts RGB→HSV, `inRange` with tolerance (40,100,100) (H,S,V), hue wraparound must work. Channel order: the Pi receives **RGB**, OpenCV conversions expect **BGR** — don't mix them up.
- **Angle:** `atan2(center_y - cy, cx - center_x)` in degrees `% 360`; 0° = right, CCW.
- **Gates on the Pi start disabled** (`enabled: False`) and track nothing until colors arrive (or a saved-colors file is loaded — Idea 3). A slot with default full-range thresholds = "not configured" (`slot_configured()`): don't track it, don't draw it.
- **UI contracts:** `unikostyl.py` creates the pygame window at import time (never import it headless); `main_loop_frame(frame_rgb)` → `(angle, {gate_id: rgb})`, called once per frame; threshold slots 1..3 = gates 1..3; **nothing is drawn on the frame itself** (no text, no bbox) — status lives in widgets/console only.
- **Ports:** 5555 video, 5557 colors, 5567 test, **5559 — camera control (settings), reserved**.
- **Contract files:** `saved_gates.json` (saved gate colors, Idea 3), `camera_settings.json` (camera settings, Idea 1), `distance_calib.json` (distance calibration, Idea 6), `field_map.json` (field binding and map, Ideas 10–11) — schemas in section 5. Writes are **atomic** (tmp + rename): the Pi may lose power mid-match.
- **Forbiddens:** do not reintroduce auto-exposure (stable colors frame-to-frame matter more); do not delete `rpi_elp_cam.py` until the C++ core is accepted on the Pi; do not use low camera modes (720p and below) as "downscaling" — they are sensor crops, full FOV is only 1920×1080 with software downscale.

**League regulation facts — RoboCupJunior Soccer, IR leagues ("Autonomous robofootball RoboCup infrared")** — official rules: `https://robocup-junior.github.io/soccer-rules-entry/master/rules.html` (Russian tournaments have local variations — verify against the specific competition's rules and make all dimensions configurable):
- Field 110–160 cm × 180–225 cm; walls 10–25 cm (matte black); floor — green carpet; white marking lines 20 mm ±10%. In the walled variant (Entry) there is no leaving the field at all; in local wall-less variants (e.g., field 1220×1830 mm with a 300 mm white border strip) crossing the boundary is a violation. **User-confirmed 2026-11-17: the venue is WALLED (Entry variant)** — physically no leaving the field; the boundary detector (Idea 11) is auxiliary/lower priority; keep dimensions configurable in case the venue changes.
- Goals: inner width 45–60 cm, depth 74 mm, height = wall height; one **yellow**, the other **blue** (these are exactly the gate tracking colors).
- Leaving the field / knocking the ball out of play → the robot is "damaged": removed for at least 1 minute (local rules — up to several minutes). The field boundary is a critical function (Idea 11).
- Ball — pulsing IR: 920–960 nm, 40 kHz carrier, 1.2 kHz modulation, ⌀74 mm (Entry); 2:2 leagues move to an orange IR ball ⌀42 mm. **The camera does not track the ball without an explicit assignment** — the ball is found by IR receivers.
- Match: 2 halves of 10 minutes; a goal is scored when the ball touches the back wall of the goal.

### Idea 5 — Gates are not "scattered": blob clustering and stability
Problem: after capturing a color (e.g., accidentally matching a t-shirt/object color), the mask appears as small pieces in different parts of the frame. Gates at competitions are always in one place, BUT an opponent robot stands in front of the gate and can split it into pieces — so close pieces must merge and far small bits must be discarded. Reference pipeline (per the user's photo): mask → erode + dilate (denoise) → largest object via `minEnclosingCircle` → angle via `atan2` → radius → distance. Requirements:
- **Morphological cleanup:** after `inRange` — morphologyEx OPEN (erode+dilate), kernel size is a configurable parameter.
- **Merging close pieces into one gate:** components with a gap < `merge_gap_px` (configurable, default ~2-3% of frame width, tune on a live picture) are ONE gate (the gap = the opponent's body). Implementation: dilate the mask by the merge radius before `connectedComponentsWithStats`, or cluster components by gap. The result is one object: `moments` (center/angle) + `minEnclosingCircle` (radius/size).
- **Discarding "scattered" pieces:** `min_gate_area` (configurable, scales with resolution) — small bits are not a gate; a component farther than `max_stray_px` from the centroid of the main pieces is a foreign object (t-shirt) — discard it. At most one gate object per color.
- **Hysteresis so the robot doesn't "go insane":** a gate is considered lost only after N consecutive empty frames (default 5, configurable) — and only then is `G<id>,-1,0` sent (contract format unchanged, only the trigger moment changes); a new detection is accepted after M consecutive frames; with two competing clusters (t-shirt + gate), stick to the cluster nearer the gate's previous position until the new one is stable for M frames.
- Implement it in Python (`rpi_elp_cam.py` + laptop tracking) **and then in the C++ core of Idea 4 — logic parity**. Performance: `connectedComponentsWithStats` + morphology at 640×360 are cheap; no findNonZero/boundingRect; stage timings to the log. Legacy `mirror_unwrap.py` — reference only, don't revive it.

### Idea 6 — Gate distance from gate size (calibration)
- Take the gate size from the merged cluster of Idea 5: width or `minEnclosingCircle` radius in px (step 5 of the reference).
- Model — the empirical curve from the reference: `d = a / (b - r) - c`, where r — object radius/half-width in px, d — distance in cm; the constants a,b,c are fitted from calibration points (robot at known distances → record r). Store the constants in **`distance_calib.json`** (atomic write, schema: `{"version":1,"model":"a/(b-r)-c","a":...,"b":...,"c":...,"points":[[r_cm,r_px],...],"ts":...}`). Cross-check/fallback without calibration — the existing model `Z = KNOWN_TARGET_WIDTH_CM * (w/π) / w_px` in `unikostyl.py`.
- **Calibrator:** a mode/script collecting pairs (known distance → measured r) and fitting a,b,c (4-6 points), writing the JSON. It must work with the live camera and with saved frames.
- **Garbage protection (no bugs):** clamp `r < b - ε` (division!), clamp d to a working range (0..500 cm); when a gate is partially occluded by the opponent, the visible size underestimates → mark the distance unreliable (`dist_reliable: false` in the Idea 2 status JSON) and hold the last reliable value for T seconds.
- Distance output to the status JSON (Idea 2), the radar (Idea 7) and the per-second log. Implementation — Python + C++ core (parity).
- The real gate width for the analytic model comes from the rules: goal inner width 45–60 cm (facts in section 4); the specific tournament's value is a parameter.

### Idea 11 — Field boundary: phototransistor board + camera (fusion)
Motivation: leaving the field = the robot is "damaged", removed for at least a minute (rules facts in section 4). Today the boundary is seen only by the Arduino with a reflectance board: **phototransistor + LED, the phototransistor wired as a common-collector amplifier**. Requirement: the robot detects the field boundary **via both the line board and the camera**, together.
- **Camera boundary detector:** floor — green carpet, markings — white 20 mm lines, outside the field — table/black surface/border strip. From the downward view (RING/directed view), estimate the presence and distance of the field edge in sectors around the robot (8–12 sectors): a separate HSV range for the floor (+white line), the share of "non-floor" in a sector → "edge close". Cheap: downscale + HSV + per-sector thresholds, no heavy segmentation. Implemented in Python and the C++ core — parity.
- **Fusion:** danger in a sector = (camera sees the edge) OR (line board triggered). The board state is not at the Pi today — the same additive reverse channel as in Idea 10 (e.g., sensor states in a telemetry line). If the channel is not implemented, the camera detector works as a standalone "adviser" and blocks nothing.
- **Output:** status JSON (Idea 2) — "edge close" flags/sectors; radar (Idea 7) — highlighting of dangerous sectors and a field outline from `field_map.json`; Arduino — only via an agreed additive message (e.g., `EDGE\n`), Arduino behavior unchanged by default.
- **No false positives:** configurable thresholds (in `field_map.json`, calibrated on the real field), hysteresis — danger confirmed by 2–3 consecutive frames; board readings take priority over the camera. Test on recorded frames of the real field, not only on synthetic ones.
